# Web UI — FastAPI backend + browser front end

**Date:** 2026-09-16
**Status:** in progress
**Branch:** `feat/web-ui`

## Why

Everything today runs through `uv run camera-orchestrator <verb>`. At the scope,
in the dark, that means typing long commands with `--iso 3200 --shutter 2
--lights 32` while the camera is auto-powering-off behind you. Three specific
pains drove this:

1. **Focus is the single biggest quality lever and it has no UI.** Live view
   exists only as `tools/liveview_demo.py` — a gitignored script that opens an
   OpenCV window. It works, but it is not part of the product, it can't be
   reached from a phone, and it can't be running while you capture.
2. **Capture settings are retyped every time.** ISO, shutter, session name and
   frame counts are the same four values all night, re-entered per command.
3. **`incoming/` is unmanageable.** Sessions accumulate as `<YYYYMMDD>-<name>`
   folders with `session.json` manifests and thousands of RAW files. There is no
   way to see what a session actually holds without `cat`-ing JSON.

A real session this month also produced two concrete failures a UI prevents: a
sequence was started with the wrong `--name` (M33 frames landed in a
`double-cluster` folder), and a run crossing midnight split one night across two
date-prefixed folders.

## Decision

**FastAPI backend + browser front end, served natively on the observing machine.**

Two decisions were considered and settled:

- **Web over desktop GUI.** `CLAUDE.md:27-28` and
  `docs/20260722-hexagonal-architecture.md:26-38` already name a future FastAPI
  layer under `interfaces/` as the intended second inbound adapter. Live view is
  an `<img src="/liveview.mjpg">` one-liner in a browser versus a manual frame
  pump into a Tk canvas. And the browser reaches the phone — useful when the
  laptop is under a dew shield and you are at the eyepiece.
- **Native, not containerised.** gphoto2 claims the USB device directly and the
  adapter releases the gvfs auto-mount before doing so
  (`adapters/camera/gvfs.py:19`). USB passthrough into a container makes PTP
  fragile and the gvfs release murky across the boundary, for no gain on a
  single-user local tool.

```
browser ──HTTP──▶ FastAPI (interfaces/api/) ──▶ application services ──▶ ports
  │                                                                       ▲
  └── <img src="/liveview.mjpg">                                    adapters
                                                              (gphoto2 ── USB ── camera)
```

## The dependency rule still holds

Nothing here relaxes the architecture. The API is an **inbound adapter** and
obeys the same rule the CLI does:

- API code lives in `camera_orchestrator/interfaces/api/`.
- It calls `composition.build_*` factories and **never** imports an adapter,
  `gphoto2`, `cv2`, `docker` or `astropy`.
- It builds the **existing** Pydantic DTOs (`CaptureRequest`, `AlignRequest`,
  `SequenceRequest`) — no parallel request shapes.
- All new wiring goes in `composition.py` and nowhere else.
- `domain/` stays runtime-pure. `fastapi` must never appear in a domain import,
  the same way `argparse` never does.

The front end is served as static assets from inside the package so
`[tool.setuptools.packages.find]` keeps working without a second top-level
package.

## Blockers found in the existing code

Surveying the codebase before building turned up five things that would have
forced the API to duplicate logic or deadlock. They are being fixed first, as
foundations, before any HTTP code is written.

| # | Problem | Where | Fix |
|---|---------|-------|-----|
| 1 | **USB device is claimed exclusively.** `build_camera()` opens a fresh PTP session per call; `CaptureService` wraps each workflow in `with self._camera_factory() as camera:`. A live-view stream and a capture request collide with `[-53] Could not claim the USB device`. | `composition.py:32`, `capture_service.py:99` | A single-owner `CameraSession` in the application layer, lock-guarded, handing out a non-closing proxy. Live view acquires per-frame so a capture waits ~100 ms, not forever. |
| 2 | **`Camera` port has no preview method.** Live view exists only in the gitignored demo script. | `domain/ports/camera.py` | Add `capture_preview() -> bytes` (raw JPEG — keeps numpy out of the domain and feeds MJPEG with no re-encode). |
| 3 | **No `BatchSolveService`.** The whole batch workflow is inlined in the CLI with `sys.exit` as control flow. | `interfaces/cli.py:36-108` | Extract to `application/batch_service.py` with a progress callback. |
| 4 | **`_resolve_session` takes an `argparse.Namespace`.** Unusable from an API, and align/sequence must agree on the folder or a night splits in two. | `interfaces/cli.py:161-174` | Extract to `application/session_paths.py` taking plain args + an injectable date. |
| 5 | **`grab_service.poll()` never returns.** `while True` + `time.sleep`, exits only on `KeyboardInterrupt`. | `application/grab_service.py:40-65` | Do not call from the API process. Needs a `stop` event + `on_file` callback before it can be exposed. |

Not a blocker but worth recording: `SequenceService.run` forwards no `on_frame`
to its capture calls (`sequence_service.py:83,86`), so a sequence reports
per-phase progress only. A live frame counter in the UI needs `on_frame`
threaded through `_phase_request`.

## Constraint: one process owns the camera

`composition.build_camera_session()` returns a **process-wide singleton**, because
libgphoto2 claims the USB device exclusively. That has consequences for where this
can run, and they get sharper if the API later becomes fully asynchronous or fans
work out across workers:

- **Do not run uvicorn with `--workers > 1`.** Each worker is a separate process
  with its own `CameraSession`, so the second one to touch the camera fails with
  `[-53] Could not claim the USB device`. The single worker is load-bearing, not
  an oversight.
- **Threads within the process are fine** — that is what the session is for. Job
  runners are daemon threads and the session serialises them behind an `RLock`,
  so parallel *processing* (solving, stacking, file work) can scale out freely.
  Only the hardware borrow is serialised, and only while it is actually held.
- **Camera-free work already parallelises.** `batch` and `solve` never borrow the
  camera and run alongside a camera job today.
- If the camera ever needs sharing across processes, the session has to move
  behind a port — one owning process the others talk to. A second uvicorn worker
  is not a substitute and fails at runtime, not at start-up.

Live view is gated on `CameraSession.in_use` (an actual borrow), **not** on job
state. This matters for the async future: job bookkeeping is a proxy that drifts
from reality, whereas a borrow count stays true however many workers or threads
are in play. An earlier version gated on "a camera job is running", which blanked
live view for the whole of an align's ~15 s plate solve — during which the camera
is idle and perfectly able to stream.

## Live updates: ONE WebSocket, never a stream per job

`WS /api/ws` carries **every** job update for the page, and takes `confirm` and
`cancel` back the other way. There was briefly a `GET /api/jobs/{id}/events` SSE
stream per tracked job. It is gone, and it must not come back.

**Why.** A browser allows roughly **six concurrent HTTP/1.1 connections per
origin**. The UI permanently spends one on live view — `<img
src="/api/camera/liveview.mjpg">` is a response that never ends. Each tracked job
took another, `EventSource` re-dials forever on error so a dropped stream never
gave its slot back, and the status poll, config and browse fetches need slots
too. After a handful of jobs the budget was gone.

An exhausted budget **does not fail — it queues, indefinitely**. Measured on this
app with six never-ending responses open: `GET /api/health` returns in **35 ms**
with the budget free, and had still not returned after **8 s** with it full. Two
symptoms at the telescope traced to this one cause: "Lost the event stream for
job …" for a job that had in fact succeeded, and live view that "just would not
open anything" on retry.

Connections are now **flat in the number of jobs**: 1 WebSocket + 1 MJPEG,
whether one job runs or fifty (measured in a real browser: 1 socket after load,
still 1 after five jobs).

### The message schema

Server → client, one JSON object per frame:

| `type` | Payload | When |
|--------|---------|------|
| `snapshot` | `{jobs: Job[]}` — newest first | First frame of **every** connection |
| `job` | `{job: Job}` | Any job changed |
| `ack` | `{command, job: Job}` | This client's `confirm`/`cancel` landed |
| `error` | `{command?, job_id?, message}` | A command was rejected |
| `ping` | — | Idle heartbeat (every `WS_TICK_S`, 15 s) |

Client → server:

| `type` | Payload | Effect |
|--------|---------|--------|
| `confirm` | `{job_id}` | Same as `POST /api/jobs/{id}/confirm` |
| `cancel` | `{job_id}` | Same as `POST /api/jobs/{id}/cancel` |
| `pong` | — | Heartbeat answer |

An unknown `type` is answered with an `error` and the socket stays open — a bad
command must never cost the page its one connection. The POST routes remain as a
tested fallback, and are what the client uses while it is reconnecting.

### Why the snapshot is the whole design

`snapshot` is not a convenience: it is what makes a dropped connection
**self-healing**. The client treats it as authoritative and overwrites, so a job
that reached a terminal state while the socket was down is corrected on the next
connect. The per-job streams had no such path — `jobs.js` reported the drop and
did nothing else, leaving a finished job stuck non-terminal in the client, which
in turn left `isExposing` true and **live view paused for the rest of the
session**. The client reconnects with backoff (400 ms → 10 s) and treats three
missed heartbeats as a dead connection, because a half-open socket otherwise
hangs silently forever.

### Implementation notes

- `JobRegistry` gained a registry-wide change cursor alongside the per-job one:
  `_revision`, `revision()` and `wait_any(revision, timeout)` — "did *anything*
  move?" rather than "did *this job* move?". The per-job `version`/`wait` API is
  untouched.
- The registry is thread-based (`threading.Condition`) and the endpoint is async.
  Every blocking registry call is bridged with `anyio.to_thread.run_sync`, with
  `abandon_on_cancel=True` on the watcher so a closed tab does not hold a worker
  thread for the rest of the tick. **Blocking the event loop here would stall
  every other request, the MJPEG stream included.**
- One task receives commands, one watches the registry, and a single sender task
  drains a bounded queue — so two producers never interleave frames on one
  socket, and a client that stops reading drops messages rather than growing a
  queue without bound.
- Each connection has its own watcher, so several clients (laptop *and* phone)
  each get everything. Nothing assumes a single client.
- No new dependency: `websockets` already ships with `uvicorn[standard]`, and the
  front end is vanilla ES modules with no build step.

## Scope

**In:**
- Live view in the browser, with digital zoom for focus.
- Capture controls: ISO, shutter, aperture, frame counts, session name.
- `align` and `sequence` driven from the UI, including the lens-cap prompt
  (`before_phase` becomes a UI confirmation instead of `input()`).
- A session/file browser over `incoming/` — what sessions exist, what each
  recorded, and what is actually on disk versus only on the card.

**Out (for now):**
- Authentication. Binds to localhost; this is a single-user tool on a laptop.
- Exposing `grab --poll` (blocker #5).
- Any change to the stacking workflow — Siril stays a separate manual step.
- The motorised platform (`docs/20260723-motorised-platform-tracking.md`
  remains parked).

## Conventions every contributor to this branch follows

These are the existing house rules, restated because several agents are working
in parallel on this branch:

- **Absolute imports** across layers. Relative only for same-package siblings.
- **A service never imports an adapter.** It takes injected factories/ports;
  `composition.py` supplies the concrete type.
- **New code lands with its test.** Inject fakes first; patch second, and patch
  at the module that imported the symbol
  (`patch("camera_orchestrator.application.batch_service.solve_file", ...)`).
- **Reuse the existing fakes** — `MockCamera` (`tests/test_service.py:15`),
  `MockSolver` (`tests/test_pipeline.py:15`), `FakeRepo`
  (`tests/test_sequence_service.py:35`). Cross-file mock imports are established
  practice here (`tests/test_align_service.py:19-20`), which is why `tests/` is
  an importable package.
- **Test style:** module docstring naming the unit and the fake strategy,
  `from __future__ import annotations`, flat `def test_*`, private `_builder()`
  helpers, trailing `#` comments on assertions explaining the *why*, `tmp_path`
  for anything on disk.
- **Do not reformat existing code.** ruff runs on defaults (`E4,E7,E9,F`);
  `E501` is not enabled, so the codebase's ~100-char lines are intentional.
- **Never hand-edit `VERSION`** — `.github/workflows/auto-release.sh` owns it.
- **PR titles must match** `.github/workflows/pr-validation.yml`. Use `feat:` so
  the release automation bumps minor.
- `.gitignore` needs `node_modules/` and a build-output entry **if** a JS
  toolchain is introduced. Prefer no build step.
- Note `*.jpg` is gitignored but `*.JPG` is not — new lowercase `.jpg` assets
  silently will not commit.

- All pre-existing tests still pass; the CLI's behaviour and log output are

  1. `uv run camera-orchestrator serve`, open the UI.
  2. Enable live view on the body, confirm the stream renders and zoom works.
  3. **While the stream is running**, fire a capture — it must succeed, and the
     stream must resume after. This is the test that proves blocker #1 is fixed.
  4. Run an `align`, confirm the solved RA/Dec and preview appear.
  5. Browse `incoming/`, confirm a card-only session shows recorded frames as
     not-on-disk rather than silently reporting zero.
- Job socket, in a real browser (no hardware needed — see the message schema
  above):
  1. Run several jobs and count connections. There must be exactly **one**
     WebSocket and one MJPEG, and the count must not grow with the job count.
  2. Kill the socket mid-job and block its reconnect until the job has finished.
     The panel will read `running` while blind; on reconnect it must converge on
     the true terminal state and release live view. Anything less is the
     stale-state bug returning.
  3. Zero uncaught console errors, in both `?mock=1` and against a real backend.
